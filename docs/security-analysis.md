# Анализ работы инструментов безопасности

## Инструменты

| Инструмент | Что проверяет |
|---|---|
| Semgrep 1.179 | код, Dockerfile и workflow (наборы правил `p/python`, `p/security-audit`, `p/secrets`, `p/dockerfile`, `p/github-actions`) |
| Trivy 0.75 `config` | мисконфигурации Dockerfile |
| Trivy 0.75 `image` | уязвимости пакетов внутри собранного образа |
| Gitleaks 8.30 | секреты во всей истории коммитов |

Semgrep и Trivy config работают в job `security`, Trivy image — в job
`release` после сборки образа. `release` объявлен через `needs: security`,
поэтому при провале проверок версия не выпускается.

## Что нашли инструменты

Первый прогон:

| Инструмент | Находок |
|---|---|
| Semgrep | 13 |
| Trivy config | 1 (HIGH) |
| Trivy image | 173, из них с доступным исправлением 7 |
| Gitleaks | 0 |

**Trivy config, DS-0002 (HIGH).** В Dockerfile не было инструкции `USER`,
контейнер работал от root (`uid=0`). При уязвимости в приложении это
упрощает выход за границы контейнера.

**Trivy image.** Из 173 уязвимостей действий требовали только 7,
остальные 166 — пакеты Debian, для которых исправление ещё не выпущено
(`will_not_fix`, `fix_deferred`). Требовали действий:

- 6 уязвимостей в pip 25.0.1, который попадал в образ из базового:
  CVE-2026-13346, CVE-2026-6357, CVE-2026-8643, CVE-2026-3219,
  CVE-2025-8869, CVE-2026-1703;
- CVE-2026-103111 (HIGH) в libpcre2-8-0 — запись за границами буфера,
  исправление в Debian уже вышло, но базовый образ собран раньше.

**Semgrep, `github-actions-mutable-action-tag` (13 находок).** Все actions
подключались по изменяемому тегу (`actions/checkout@v4`). Тег в Git можно
перенести на другой коммит, поэтому компрометация репозитория action даёт
исполнение чужого кода в пайплайне с доступом к `GITHUB_TOKEN`. Так в
2025 году был скомпрометирован `tj-actions/changed-files`
(CVE-2025-30066), а в 2026 — `trivy-action` (CVE-2026-33634).

## Слабые места, которые инструменты не нашли

По коду приложения Semgrep дал 0 находок: он ищет известные небезопасные
конструкции, а дефекты калькулятора относятся к обработке входных данных.
Они нашлись проверкой граничных значений:

| Запрос | Было |
|---|---|
| `{"a":1e308,"b":2,"operation":"**"}` | 500, `OverflowError` |
| `{"a":0,"b":-1,"operation":"**"}` | 500, `ZeroDivisionError` |
| `{"a":-8,"b":0.5,"operation":"**"}` | 500, Python вернул комплексное число |
| `{"a":1e300,"b":1e300,"operation":"*"}` | 200 и `{"result":null}` |
| `{"a":1e400,"b":1,"operation":"+"}` | 200 и `{"result":null}` |

Первые три позволяют одним запросом без аутентификации получать 500 и
записи в журнал ошибок. Последние две опаснее: приложение отвечает кодом
200 и молча отдаёт неверный результат.

Ещё одно место нашлось при исправлении: после запрета `inf` на входе
стандартный обработчик `RequestValidationError` в FastAPI возвращает в
ответе присланное значение, и на `inf` сериализация ответа падала —
вместо 422 снова получался 500.

Вывод: SAST и сканирование образа закрывают известные шаблоны и состав
зависимостей, но не проверяют корректность обработки граничных значений.

## Что исправлено

| Находка | Исправление |
|---|---|
| root в контейнере | `useradd appuser` и `USER appuser` в Dockerfile |
| 6 CVE в pip | pip удалён из образа после установки зависимостей, в рантайме он не нужен |
| CVE-2026-103111 | `apt-get upgrade` при сборке, сборка с `--pull` |
| изменяемые теги actions | закреплены по SHA коммита, в Dependabot добавлена экосистема `github-actions` |
| 500 на переполнении и `0 ** -1` | `try/except OverflowError, ZeroDivisionError` → 400 |
| молчаливый `null` вместо результата | `allow_inf_nan=False` на входе (422) и проверка `math.isfinite` для результата (400) |
| 500 в обработчике ошибок валидации | свой обработчик `RequestValidationError` без поля `input` |

Результат второго прогона:

| Инструмент | До | После |
|---|---|---|
| Semgrep | 13 | 0 |
| Trivy config | 1 HIGH | 0 |
| Trivy image, с исправлением | 7 | 0 |
| Trivy image, всего | 173 | 166 |
| Gitleaks | 0 | 0 |
| Тестов | 4 | 13 |

Также исправлены закоммиченные в `main` маркеры конфликта слияния в
`VERSION`, `README.md` и `ci.yml`: workflow был невалидным YAML, то есть
пайплайн не запускался, а приложение падало при чтении версии.

## Порог блокировки пайплайна

Semgrep, Gitleaks и тесты останавливают пайплайн на любой находке,
Trivy config — на уровне MEDIUM и выше, Trivy image — только на CRITICAL,
для которой доступно исправление (`--ignore-unfixed`). Блокировка по
общему числу находок в образе сделала бы пайплайн нерабочим из-за 166
уязвимостей базового образа, которые разработчик приложения устранить не
может.

## Предложения

1. Перейти на базовый образ `distroless` или `alpine` — это основной
   способ убрать оставшиеся 166 уязвимостей, в таком образе нет ни
   оболочки, ни менеджера пакетов.
2. Закрепить базовый образ по digest (`python:3.12-slim@sha256:...`) и
   обновлять через Dependabot: тег `3.12-slim` изменяемый так же, как
   теги actions.
3. Ограничить частоту запросов к `/calculate` — сейчас ограничений нет.
4. Включить защиту ветки `main` с обязательным прохождением проверок:
   сейчас изменения попадают в `main` напрямую, именно так в репозиторий
   и попали маркеры конфликта слияния.
5. Публиковать SBOM (`trivy image --format cyclonedx`) и подписывать
   образы, чтобы можно было проверить их состав и происхождение.
6. Закрыть `/docs` и `/openapi.json` в производственном окружении.
